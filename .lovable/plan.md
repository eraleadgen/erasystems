# Two installable apps per client (browser install only)

Each client ends up with two separate installable apps, gated behind the
White-Label add-on:

1. **Customer app** — their public site and booking flow, installed from their own
   domain by their customers.
2. **Team app** — the portal (dashboard, plus customer/specialist portals their tier
   actually includes), installed from the ERA app address by the business and staff.

They never collide, because they live on different addresses: the customer app is
served from the client's own domain, the team app from the ERA portal address. Each
address gets exactly one app identity.

## Per-business manifest (not one shared file)

No static manifest file. Two small server endpoints build the manifest per request:

- `/site.webmanifest` — resolves the business from the incoming hostname, exactly the
  way the public site already resolves a tenant. Unknown host, no business, inactive
  business, or White-Label not active → plain 404, no app identity offered.
- `/portal.webmanifest?b=<business_id>` — resolves the business from the signed-in
  member's own record, not from the address bar, then re-checks the add-on.

Each response is built from that business's stored name, logo and brand colours:
short name, full name, theme colour, background colour, `standalone`, and start
addresses (`/` for the customer app, `/dashboard` for the team app). The team app's
name is suffixed ("<Business> Team") so the two icons on a phone are distinguishable.
Responses are marked private and short-lived so one client's identity is never served
to another.

## Icons, and the client with no logo yet

Icons are generated per business, also per request, from a small image endpoint
(`/app-icon/<business_id>/<size>`):

- **Logo uploaded** → their logo, centred on their brand background, at each required
  size, plus a maskable variant with safe padding so Android doesn't crop it.
- **No logo** → a generated monogram tile: their initials in their brand colours. Not
  an ERA logo, and not a broken image — a client who never uploads anything still gets
  a correct, on-brand icon, and it silently upgrades the moment they upload one.

Image generation runs in the app's own server layer with a lightweight vector-to-PNG
path (no native image libraries — those don't run in this hosting environment). Icons
are cached by business and revision so repeat installs are cheap.

## Service worker

One generated service worker, shared code, tenant-neutral by design: it caches only
the built app files and always fetches pages fresh, so it can never serve one tenant's
page to another. It is generated by the standard build tooling (not hand-written), and
registers only on the published site — never in the editor preview, never in an iframe
— with a `?sw=off` escape hatch. Offline use is limited to "the app opens and shows a
cached shell"; live data still needs a connection.

Registration is additionally skipped when the business does not have White-Label active,
so a non-add-on client's site behaves exactly as it does today.

## White-Label gating

Reuses the existing add-on check with no new access path:

- Manifest endpoints and the install prompt return nothing unless
  `business_addons` has an active `white_label_branding` row for that business.
- Turning the add-on off removes the manifest and stops new installs; already-installed
  copies keep working until removed, which is a browser behaviour we can't revoke — the
  plan says so plainly rather than pretending otherwise.
- Staff toggle it from the existing add-ons screen; nothing new to manage.

## What clients see

- Add-on active, on their site: browser offers "Install app"; an in-page prompt appears
  once for supported browsers, dismissible.
- iPhone/iPad: Safari has no install button — the same prompt shows the Share → Add to
  Home Screen instruction instead, with their icon.
- Portal: same prompt inside `/dashboard` for owners, staff and (where their tier
  includes it) customers and specialists.

## Acceptance test before this is called done

A throwaway client with White-Label active and **no logo**: install from its own domain,
confirm the home-screen icon shows its monogram in its own colours and its own name, and
that installing the portal from the ERA address produces a second, separate icon. Upload a
logo, reinstall, confirm the icon changes. Then a second client with the add-on off:
confirm no manifest, no install offer, and confirm the first client's manifest and icon
are never returned on the second client's address.
